## 2. آلية تحديد المتجر (Store ID Resolution)

تم تصميم وتطبيق بنية مركزية خالية من التشتت (`src/lib/store-config.ts`):

```text
               Environment Check
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
Vite Client/Build                Node / Server / Worker
(import.meta.env.VITE_STORE_ID)   (process.env.STORE_ID)
       │                               │
       └───────────────┬───────────────┘
                       ▼
             UUID Validation Regex
                       │
             ┌─────────┴─────────┐
      [Valid UUID]         [Invalid / Missing]
             │                     │
             ▼                     ▼
      Active Store ID      DEFAULT_SHAHID_STORE_ID
                    ("7a3c8e14-6b92-4f8e-9d21-4c5e7b8a9f01")
```

### تصنيف المعرفات والمتغيرات:
1. **Public Store Identifier (`STORE_ID` / `VITE_STORE_ID`):** معرّف عام غير سري متاح للمتصفح والخادم، وظيفته تحديد نطاق القراءة والكتابة فقط.
2. **Server Environment Variables (`wrangler.jsonc` vars):** محقونة لكل Cloudflare Worker على حدة لكل متجر عند النشر (مثلاً `STORE_ID` الخاص بشاهد في worker شاهد، و `STORE_ID` الخاص بكوبرا في worker كوبرا).
3. **Sensitive Secrets (`SUPABASE_SERVICE_ROLE_KEY`, `EDFAPAY_API_KEY`):** أسرار مشفرة لا تمر إلى المتصفح أبداً وتُحقن كأسرار في بيئة تشغيل الخادم.

## 3. كتابة البيانات في قاعدة البيانات (Database Writes)

* **إنشاء الطلبات الجديدة (`orders.insert`):**
  أصبح كائن الطلب في مسار Checkout المباشر وفي مسار بطاقة الائتمان (EdfaPay) يمرر `store_id: STORE_ID` بشكل صريح ومباشر:
  ```ts
  const payload = {
    id: orderId,
    store_id: STORE_ID, // صريح ومباشر
    order_number: orderNumber,
    customer_name: data.customer_name,
    ...
  };
  ```
* **إنشاء المنتجات الجديدة (`products.insert`):**
  يمرر `store_id: STORE_ID` صراحة (موجود ومؤكد في `createAdminProduct`).
* **إنشاء التصنيفات الجديدة (`categories.insert`):**
  يمرر `store_id: STORE_ID` صراحة (مؤكد في `createAdminCategory`).
* **إنشاء الكوبونات الجديدة (`coupons.insert`):**
  يمرر `store_id: STORE_ID` صراحة (مؤكد في `createCoupon`).
* **الوضع بالنسبة لـ Database Default و Trigger:**
  * تم الإبقاء على القيمة الافتراضية لقاعدة البيانات والـ Trigger `trg_ensure_store_id` دون حذفهما لحماية متجر Shahid الحالي من أي تعطل غير مقصود (Backward Compatibility).
  * أصبح الكود البرمجي لا يعتمد على الـ Default بتاتاً في مسارات الكتابة المحصنة.

## 5. نتائج عزل لوحة التحكم (Admin Isolation)

1. **المنتجات والتصنيفات:**
   جميع استعلامات `fetchAdminProducts` و `fetchAdminCategories` تم تزويدها بفلتر صريح `.eq("store_id", STORE_ID)`. وبذلك حتى وإن كان حساب المدير يمتلك صلاحية `is_admin() = true` التي تتجاوز الـ RLS، فإن استعلامات الواجهة الأمامية تحصر العرض تلقائياً بمنتجات المتجر النشط.
2. **الطلبات والسلات المتروكة:**
   تعديلات وحذف واستعلامات الطلبات مقيدة بالمتجر النشط. تم تأمين دوال الحذف والتنظيف الجماعي (`cleanupAbandonedOrders`) بـ `.eq("store_id", STORE_ID)`.
3. **الكاش (TanStack Query Cache):**
   تم تحديث جميع مصفوفات `queryKey` لتشمل `STORE_ID`، مما يضمن أنه في حال التبديل أو تعدد الجلسات، لا تختلط بيانات الكاش في المتصفح.

## 6. نتائج عزل مسار Checkout

* **إنشاء الطلب:** الطلب المنشأ يحمل الآن معرف المتجر الصريح، ويتم حفظه برمجياً مع المتجر الصحيح.
* **فحص الكوبونات:** لا يمكن لعميل في متجر شاهد تفعيل كود خصم خاص بمتجر آخر، نظراً لتقييد فحص الكوبونات في جهة العميل وجهة الخادم بـ `.eq("store_id", STORE_ID)`.
* **استعراض الطلب بعد الشراء:** دوال استعراض الطلب (`getCustomerOrderView`, `getMyOrderView`) تتحقق من أن الطلب المستعرض يتبع المتجر الحالي.

## 9. المخاطر المتبقية والاعتبارات المعمارية (Remaining Risks)

1. **جدول إعدادات المتجر القديم (`store_settings`):**
   * كشف التدقيق أن جدول `store_settings` الحالي مفتاحه الأساسي هو `key text PRIMARY KEY` ولا يمتلك عمود `store_id`.
   * تم الحفاظ عليه ليعمل مع متجر Shahid دون المساس به لتفادي كسر إعدادات الواتساب الحالية.
   * بالنسبة لمتجر Cobra والمتعدد، يتم استخدام حقل `settings jsonb` داخل جدول `stores` أو تنفيذ ترحيل لاحق لإضافة `store_id` بمفتاح مركب `(store_id, key)` عند الجاهزية.
2. **جدول الحسابات التخزينية (`inventory_accounts` / `subscription_inventory`):**
   * الاشتراكات المسلمة ترتبط حالياً بالطلب (`order_id`)، والطلب مرتبط بالمتجر (`store_id`). وبالتالي يتم عزل التسليم تلقائياً عبر الطلب. ولكن عند تخصيص مخزون مستقل مسبق لمتجر Cobra، سيحتاج جدول حسابات الاشتراك إلى حقل `store_id` مستقل.
3. **دوال SQL المخزنة (Stored Procedures / RPCs):**
   * دوال الـ RPC القديمة مثل `validate_coupon_code` تبحث في جدول الكوبونات بالكود. قمنا بتدعيم التحقق بحماية ثنائية (Fallback بـ `store_id` مباشر). يُفضل مستقبلاً تحديث الـ RPC لقبول `_store_id uuid`.
